## 引言

现代软件工程师的大部分工作 [^1] 都离不开 API，也就是程序暴露给外部使用的接口。这些年，我设计过，也使用过很多 API：既有面向第三方开发者的公共 API，也有内部 API（甚至只是给一个前端页面使用）；做过 REST、GraphQL，也设计过命令行工具这类非网络接口。

我认为网上流传的很多 API 设计建议都过于追求理论（炫技）了。大家总喜欢争论什么才是「真正」的 REST，或者 HATEOAS 有没有必要，等等。这篇文章尝试把我所知道的所有优秀 API 设计写下来。

## 好的 API，是无聊的

如果说这条规律对系统设计成立，那它对 API 设计就更成立。**好的 API，应当是无聊的**。一个让人觉得「有意思」的 API，多半不是一个好 API。（或者说，如果它没那么有趣的话，会变得更好）。对于 API 的设计者来说，API 是需要反复设计、不断打磨的产品；但对用户来说，API 只是完成工作的工具。花在理解 API 上的时间，都是额外成本。从他们的视角看，理想的 API，应该让开发者几乎不用看文档 [^2]，就知道怎么用。

然而，API 与大多数软件系统的一个重大区别在于，**API 一旦发布，就很难再改**。一旦你发布了一个 API 并且有人用了，任何接口变更都可能破坏用户。当然，也不是说不能变更，只是每一次变更，都会让用户付出不小的代价。他们会重新评估，是不是该换一个更稳定的 API。这给 API 设计者带来了动力：好好设计 API，争取第一次就把它做到最好。

这种矛盾给 API 设计者带来了有趣的挑战。一方面，他们设计尽可能简单的 API；另一方面，他们又想用巧思来保持灵活。归根结底，API 设计就是在这不相容的两者之间寻找平衡。

## 绝对不要破坏用户空间

当你需要变更 API 时会发生什么？**增量变更**，比如在响应中增加一个新字段，一般来说是没问题的。确实有些用户会因为多收到一个字段而崩溃，但那是用户的原因。你应该期望 API 用户忽略额外的未知字段（合理的 JSON 解析类型化语言默认就是这么做的）。

但是，你不能删除字段，也不能修改字段的类型。你也不能改变现有字段的结构（比如把 JSON 响应中的 `user.address` 移到 `user.details.address`）。如果这么干，每一段依赖这些字段的代码都会崩溃。用户会把它当成 Bug 提交；等维护者查清原因，多半会气个半死。

这里遵循的是 Linus Torvalds 的那句名言：[**WE DO NOT BREAK USERSPACE**](https://lore.kernel.org/all/CA+55aFy98A+LJK4+GWMcbzaa1zsPBRo76q+ioEjbx-uaMKH6Uw@mail.gmail.com/)（我们绝不破坏用户空间）。作为 API 的维护者，避免影响你的下游用户是最重要的职责。这个规范之所以如此强硬，是因为有太多软件依赖着太多 API（而这些 API 又依赖上游 API，层层递进）。一个足够上游的 API 维护者只要稍不留意，就可能破坏下游成百上千个软件。

希望你不会因为某个改动「更整洁」，或者因为某个地方「有点别扭」就去改动 API。HTTP 规范中的 `referer` 头就是著名的 `referrer` 拼写错误，但他们一直没有改，因为他们不想破坏用户空间。

## 真的要改 API，就做版本化

说实话，很难找到 API 真的需要破坏性变更的例子。但如果某个变更足够必要、有价值，你咬咬牙还是决定要改，那在这种情况下，如何负责任地变更 API？答案是 **版本化**。

API 版本化，就是让新旧版本长期共存。现有的用户可以继续使用旧版本，新用户可以选择接入新版本。最简单的方法是在 API URL 中加入类似 `/v1/` 的路径。OpenAI 的聊天 API 是 [`/v1/chat/completions`](https://platform.openai.com/docs/api-reference/chat/create)，所以如果他们将来想完全重构结构，可以在新的 API 端点 `/v2/chat/completions` 里做，同时现有用户不会受影响。

一旦新旧版本共存，你就可以开始提醒用户升级到新版本。这个过程往往要持续几个月，甚至几年。即使你已经在网站、文档、定制邮件和 API 响应头里反复通知提醒，当你最终移除旧版本时，仍然会有很多生气的用户来投诉，说你破坏了他们的软件。但至少你已经尽力了。

有很多其他方式做 API 版本化。Stripe 的 API 在 [header](https://docs.stripe.com/api/versioning) 里做版本控制，并允许账户在 UI 中设置默认版本。但原理是一样的，任何 Stripe API 的用户都可以放心，Stripe 绝不会破坏他们的应用，他们可以按自己的节奏升级版本。

我不喜欢 API 版本化。它或许是必要之恶，但终究还是一种恶。用户会很困惑，他们在搜索你的 API 文档时，很难确保文档版本和他们当前使用版本匹配。对维护者来说更是一场噩梦。如果你有三十个 API 端点，每增加一个新版本就新增三十个端点要维护。你会很快陷入数百个 API 都需要测试、调试和客户支持的困境。

当然，增加一个新版本并不意味着代码库翻倍。任何合理的 API 版本化后端都会有一个类似「翻译层」的东西，能把一个响应转换成你的任意一个公共 API 版本。Stripe 就有 [类似的设计](https://stripe.com/blog/api-versioning)，实际的业务逻辑在所有版本中都是一样的，只有参数序列化和反序列化需要感知版本。不过，这种抽象总会泄漏。参见 2017 年一位 Stripe 员工在 [HN 上的评论](https://news.ycombinator.com/item?id=13711171)，他指出某些版本化变更需要在「核心代码」中加入条件逻辑。

简而言之，**最好只在万不得已时才使用 API 版本化**。

## API 的成败，还是产品决定

没人会为了 API 而使用你的产品。人们真正使用的是产品本身。对 [OpenAI API](https://platform.openai.com/docs/api-reference/chat/create) 来说，那是使用语言模型进行推理的能力；对 [Twilio API](https://www.twilio.com/docs/iam/api/account#fetch-an-account-resource) 来说，那是发送短信。没人会因为你的 API 足够规范、优雅而使用你的产品。他们只是用它来与你的产品交互。如果你的产品足够有价值，哪怕你的 API 再垃圾他们也得咬着牙用。

这就是为什么一些最流行的 API 是最难用的。Facebook 和 Jira 的 API 臭名昭著，但这都是小事，如果你想集成 Facebook 或 Jira（你确实想），你就得花时间去搞懂它们。如果这些公司有更好的 API，当然更好。那既然不管 API 写的好不好，人们都会去集成，为什么还要投入时间和金钱去改进呢？写好 API 真的很难。

我将在后面给出具体的建议。但请记住，大多数时候这并不重要。如果你的产品受欢迎，有 API，能跑就行；如果产品用户都没几个，你的 API 再好也没用。大多数时候，API 的质量只是锦上添花。只有当用户必须得在两个差不多的产品之间做选择时，才会考虑 API。

顺便说一句，有没有 API 完全是另一回事。如果一个产品根本没有 API，那是个大问题。懂技术的用户肯定会想要通过代码进行集成的方式，比如 API，逃不掉的。

## 糟糕的产品，很难有好的 API

设计极佳的 API 无法拯救一个没人想用的产品。但设计得一坨的产品也不可能设计得出多么优雅的 API。API 设计通常对应着产品的「基本资源」（比如 Jira 的资源就是 [issue](https://developer.atlassian.com/cloud/jira/platform/rest/v2/api-group-issues/#api-rest-api-2-issue-issueidorkey-get)、[project](https://developer.atlassian.com/cloud/jira/platform/rest/v2/api-group-projects/#api-rest-api-2-project-projectidorkey-get)、[user](https://developer.atlassian.com/cloud/jira/platform/rest/v2/api-group-users/#api-rest-api-2-user-get) 等）。当这些资源本身被设置得不合理、很别扭时，API 也别想好到哪去。

举个例子，假设一个博客系统把评论以内存中的链表存储（每条评论有一个 `next` 字段指向线程中的下一条评论）。这种设计本身就很别扭。在这个系统上强行挂一个 REST API，最原生的做法可能是这样的接口：

```
GET /comments/1 -> { id: 1, body: "...", next_comment_id: 2 }
```

或者更糟：

```
GET /comments -> {body: "...", next_comment: { body: "...", next_comment: {...}}}
```

这个例子有点极端，因为实际中你大可以遍历链表然后在 API 响应中返回一个评论数组。但即使你愿意多做这一步，你要遍历多深？在一个有成千上万条评论的线程里，是不是就完全没法获取前几百条之后的评论了？你的评论获取 API 是不是得用后台任务，迫使接口变成类似这样：

```
POST /comments/fetch_job/1 -> { job_id: 589 }
GET /comments_job/589 -> { status: 'complete', comments: [...] }
```

那些垃圾 API 就是这么来的。那些被隐藏在 UI 底层的技术细节和约束，在 API 中却暴露无遗，强迫 API 用户去试图理解一个完全不合理的系统设计。

## API Key，比 OAuth 更重要

最好允许人们使用长期有效的 API key 来调用你的 API。是的，API key 不如各种短期凭证（如 OAuth，你也应该支持它）安全。但这不重要。几乎所有集成，都是从一个简单脚本开始的，使用 API key 能让脚本最快得跑起来。你要尽可能让用户能轻松上手。

虽然 API 的用户（几乎从定义上）是在写代码，但你的很多用户并不是专业工程师。他们可能是销售、产品经理、学生、爱好者等等。当你在科技公司以工程师身份构建 API 时，很容易想象你的用户是和你一样的人：全职、有能力、专业的软件工程师。其实不然，你的用户群体非常广泛，其中很多人根本不懂怎么写代码。如果你让用户在调 API 前先进行 OAuth 握手，估计这一步足够让大多数用户直接跑路。

## 重试，为什么不会重复执行？

如果 API 请求成功，代表操作顺利完成，这很好理解。那失败呢？某些信息会告诉你发生了什么：比如 422 通常表示请求验证阶段就挂了，没 执行任何操作 [^3]。但 500 呢？超时呢？

这对那些会执行操作的 API 来说很重要。如果你在调用某个 Jira API 来创建 issue 评论，而请求返回 500 或超时，你应该重试吗？你不确定评论是否已经创建成功，因为错误可能发生在该操作之后。如果重试，你可能会创建两条评论。如果操作结果比 Jira 评论本身更重要时，这问题就更严重了。比如你在转账？或者在配发药物？

解决方案是 **幂等性**（Idempotency），听起来很唬人，其实就是请求可以安全重试，而不会重复执行。标准做法是在请求中支持一个「幂等键」（比如在参数或 header 中放一个用户自定义字符串）。当 API 服务器收到一个带幂等键的「创建评论」请求时，它会先查一下是否见过这个幂等键。如果见过，就什么也不做；否则就去创建评论，然后保存这个幂等键。这样，只要重试使用同一个幂等键，无论发送多少次，请求都只会执行一次。

这个键应该怎么存？我见过有人把它存在某种持久化的、与资源相关的地方（比如在 comments 表里加一列），但我觉得这不是必须的。最简单的做法是放在 Redis 或类似的 key/value 存储里（以幂等键作为 key）。UUID 已足够唯一，按用户隔离也可以，但不是必须。如果你不是处理支付，甚至可以几小时后过期，因为大多数重试都是立即发生的。

每个请求都需要幂等键吗？读请求不需要，因为重复读取是无害的。删除请求通常 [^4] 也不需要，因为如果你按资源 ID 删除，这个 ID 本身就充当了幂等键。想想看，如果你连续发送三次 `DELETE /comments/32`，它不会删除三条评论。第一次成功的请求会删除 ID 为 32 的评论，剩余的请求会因为找不到已删除的评论而返回 404。

大多数情况下，幂等性不是必须的。如我上面所说，你要确保 API 对非开发人员也足够友好。从大局看，让更多人用上你的 API 比偶尔出现一条重复评论（来自那些没读文档的用户）更重要。

## API 一定会被滥用

与 UI 交互的用户受限于他们手速。如果某个流程对后端来说很昂贵，恶意或粗心的用户最多只能以他们点击的速度触发它。API 不一样。任何接口，都可能以代码的速度被调用。

要小心那些单个请求做大量工作的 API。我在 Zendesk 工作时，有一个 API 可以把通知扇出给某个应用的所有用户。某个机灵的第三方开发者 [^5] 用这个 API 构建了一个应用内聊天系统，每条消息都会给账户里所有其他用户发一条通知。当活跃用户一多，完美地搞崩了 App 后端服务器。

我们没有预料到这个 API 还能用来开发聊天应用。但一旦 API 发布，人们就会用它做各种想做的事。我参与过很多很多次故障排查，根本原因都是某个客户在自己的集成代码里抖机灵，比如：

* 每分钟创建和删除同一条记录数百次，没有任何实际理由
* 不停轮询一个巨大的 `/index` 端点，没有任何间隔
* 导入或导出大量数据，出错时也不退避

最好为 API 设置限流（Rate Limit），对昂贵操作设置更严格的限制。同时，明智的做法是保留临时禁用特定客户 API 的能力，这样可以在后端系统真的被猛烈攻击时，可以减轻服务器压力。

在 API 响应中包含限流元数据。`X-Limit-Remaining` 和 `Retry-After` 头能给客户端提供足够信息，让它们了解并遵循当前的限流措施，也允许你设置比原本更严格的限流阈值。

## 必要时分页，海量数据优先使用游标

几乎每个 API 都需要提供长列表数据。有时是非常长的列表（比如 Zendesk 的 `/tickets` API 可能包含几百万条工单）。如何提供这些记录？

一个原生的 `SELECT * FROM tickets WHERE...` 方法会撑爆你的服务器内存（如果在应用层序列化这几百万条列表）。你根本无法在一个请求中返回所有工单。你必须分页。

最简单的分页方式是使用 **页数**（通常也叫「偏移量」）。当你访问 `/tickets` 时，你得到账户上的前十条工单。要获取更多，你只能访问 `/tickets?page=2` 或 `/tickets?offset=20`。这很容易实现，因为服务端只需在数据库查询末尾加上 `OFFSET 20 LIMIT 10`。但它无法扩展到真正海量的记录。数据库需要从 offset 开始计数，因此 offset 越大，查询越慢。当 offset 达到几十万时，问题就严重了。

解决方案是 **基于游标的分页**（Cursor-based pagination）。你不用传 `offset=20` 来获取第二页，而是取第一页最后一条工单（比如 ID 为 32），然后传 `cursor=32`。API 会返回接下来的十条工单，从 ID 32 开始。查询不再是 `OFFSET`，而是 `WHERE id > cursor ORDER BY id LIMIT 10`。这个查询无论你在集合的开头还是数十万条工单之后，速度都一样快，因为数据库可以直接定位到索引位置，而不用遍历整个偏移量。

对于可能变得很大的数据集，最好始终使用基于游标的分页。虽然对用户来说更难理解，但如果你遇到扩展问题，你可能最终还是得改成游标分页，而做这个改动的成本往往很高。不过，我认为在其他情况下使用基于页数或偏移量的分页也没什么问题。

通常建议在 API 列表响应中包含一个 `next_page` 字段。这样用户就不必自己计算下一页的页码或游标了。

## 灵活的可选字段与 GraphQL

如果 API 响应的某些部分很昂贵，就把它做成可选的。比如，如果获取用户的订阅状态需要后端调用另一个 API，那你可以考虑让 `/users/:id` 端点默认不返回订阅信息，除非请求中传了 `include_subscription` 参数。更通用的做法是，你可以有一个 `includes` 数组参数，包含所有可选字段。这通常用于关联记录（比如你可以传 `includes: [posts]` 来在用户请求中同时获取该用户的帖子）。

这是 [GraphQL](https://graphql.org/) 背后的部分思想。GraphQL 是一种 API 风格，它不是按操作访问不同端点，而是让你构造一个包含所有所需数据的查询，然后后端自己处理 [^6]。

我不太喜欢 GraphQL，主要有三个原因。第一，它对非工程师（乃至很多工程师）完全不可理解。一旦你学会了，它和其他工具一样，但入门门槛比 `GET /users/1` 高太多了。第二，我不喜欢给用户自由构造任意查询的自由。这让缓存更复杂，也增加了你需要考虑的边界情况数量。第三，以我的经验，后端的实现比标准 REST API 要琐碎得多。

不过，我也没有那么排斥 GraphQL。我前前后后用过大概半年，远非专家。我确信有些场景下它能给你足够的灵活性，值得付出这些成本。但现在我只会在绝对必要的时候才使用它。

## 内部 API 可以特殊对待

我上面说的都是有关公共 API。那 **内部 API** 呢？也就是只在公司内部被同事使用的 API。我之前的一些假设对内部 API 并不成立。因为，你的内部 API 用户通常都是专业软件工程师。而且，你也可以安全地进行破坏性变更，因为：（a）用户数量往往少一个数量级，（b）你有能力去给所有这些用户部署新代码。你可以使用任何复杂形式的鉴权，只要你想。

然而，内部 API 仍然可能导致故障，关键的操作，最好还是加上幂等性。

## 总结

* API 很难设计：既要保持稳定，又要保持易用。
* API 维护者的首要职责是 **不破坏用户空间**，不要轻易对公共 API 做破坏性变更。
* API 版本化可以解决兼容性问题，但会增加实现和维护成本。
* 好产品可以弥补糟糕的 API；糟糕的产品则很难靠优秀 API 挽救。
* API 应支持简单的 API Key 鉴权，因为很多用户并非专业工程师。
* 涉及状态变更的操作（尤其是支付等高风险操作）应支持幂等键，让请求可以安全重试。
* API 总会成为故障来源，因此需要做好限流、熔断和故障隔离。
* 对可能增长到巨大规模的数据集，应优先考虑基于游标的分页。
* 将昂贵字段设计为可选项并默认关闭；GraphQL 虽然灵活，但很多场景下可能是过度设计。
* 内部 API 与公共 API 不同：用户、变更成本和维护方式都不同。

**我还漏了什么？** 我没有写 REST vs SOAP，JSON vs XML，因为我觉得这些不是特别重要。我喜欢 REST 和 JSON，但我对此没有强烈意见。我也没有提到 OpenAPI schema，它是一个有用的工具，但我觉得如果你愿意，直接用 Markdown 写 API 文档也完全可以。

*更新：这篇文章在 [Hacker News](https://news.ycombinator.com/item?id=45006801) 和 [Reddit](https://www.reddit.com/r/programming/comments/1mzqigs/everything_i_know_about_good_api_design/) 上受到热议。有人说我应该在幂等性部分提到 PUT，因为它按理说在设计上就是幂等的。也许吧，我在实践中见得不多，而且在我看来，HTTP 动词本身并没有什么东西能让它比 POST 更幂等。还有人担心使用 Redis 作为幂等存储，因为无法在 Redis 和数据库之间协调安全的原子操作。对于支付或高风险领域，这确实是个合理的担忧，但在已有的非幂等 API 上硬接一个 Redis 仍然比什么都不做强得多。*
